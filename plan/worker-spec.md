# 作業役への指示 — 毎回同じ部分

Lean の証明を作業役 (codex) に依頼するときの、**依頼のたびに変わらない部分**をここに置く。
依頼文には目標と経路だけを書き、この文書を読むよう 1 行入れれば済む。

なぜ分けるか。以前は毎回すべてを手で書き写していて、**書き写し忘れた規則はそのまま抜けた**。
実例: 最初の依頼で `native_decide` の禁止を書き忘れ、作業役はそれを 5 箇所で使った。
次の依頼でも書き忘れ、11 箇所に増えた。書いた依頼では 0 箇所だった。
作業役が規則を破ったのではなく、**知る手段が無かった**。

---

## 1. 全タスク共通

### 検証の方法

- 検証は `leanman check` だけを使う。`lake build`、`lake env lean`、`lean` を直接実行しない。
- **`-C` は必ず付ける。** このマシンの `leanman` の既定プロジェクトは別のプロジェクトなので、
  付け忘れると**別のプロジェクトに対して検証**することになる。
  (以下の絶対パスは作業機のもの。読者の環境では読み替えること — この文書は
  同じ機械で動く作業役への指示なので、あえて具体的なパスのまま書いてある。)

  ```
  leanman check -m <ラベル> -C /home/koteitan/proofs/bms-rathjen/git/lean \
      --backend lean <ファイル>.lean; echo "exit=$?"
  ```

- **判定は exit code だけで行う。** 出力の見た目で判断しない。

  | exit | 意味 |
  |---|---|
  | 0 | 通った (エラーも `sorry` も無い) |
  | 1 | `sorry` が残っている |
  | 2 | Lean のエラー |
  | 124 | 時間切れで停止させられた |

- **`lean` は成功時に何も出力しない。** したがって**出力が空であることは何の証拠でもない**。
  途中で切れたコマンドも同じく空を返す。

### プロジェクトの扱い

- Lean プロジェクトは**読み取り専用**。中のファイルを編集しない。
- 自分の作業ディレクトリの中だけに書く。
- **書く前に、使おうとしている名前をリポジトリで検索する。** 既にあるものを再導出しない。
  作業役からは、こちらが直前に取り込んだものが見えない。依頼文に列挙するが、検索もする。

### 使ってはいけないもの

- **`native_decide` は全面禁止。** このリポジトリは 1 箇所も使っていない。すべてカーネルで
  検査されている。このツールチェーンでは `native_decide` は宣言ごとに固有名の公理
  (`<宣言名>._native.native_decide.ax_N_N`) を作り、`lean/scripts/axiom_sweep.lean` が
  それを検出する。**これを含むファイルは exit 0 でも受け取らない。**
- **最終的なファイルに `sorry` を残さない。** 途中の切り分け道具として使うのは構わない。
- **`lake build` を作業役が実行しない。** `.lake` に書き込むので、同時実行すると壊れる。

### 公理の報告

- 証明した定理すべてに `#print axioms` を付け、その出力を報告に貼る。
- 目標は `[propext, Quot.sound]` またはその部分集合。
- **`Classical.choice` は数学ではなくタクティクから入る。** 詳しくは下の「公理の掃除」。

### 報告

- 最後の `leanman check` の exit code。
- ファイルの全文。
- 閉じた補題と閉じなかった補題を、**名前で**。
- exit 0 に届かなかったら、開いている目標を正確に。

**通らなかったことを正直に報告するのは成果である。** 検証していない成功の主張は、
何も報告しないより悪い。こちらで必ず検査し直すので、いずれ分かる。

### 作ったものを試験する

**証明でも、検査スクリプトでも、分類する `#eval` でも、作ったら試験を付ける。**
理由は [constitutions C0](constitutions.md)。この repo で一晩に自作の検査器が 5 回誤り、
事前に試験してあった 1 つだけが最初から正しかった。

| 作ったもの | 試験の形 |
|---|---|
| 検査器・スクリプト | 捕まえるはずの欠陥を 1 つ与えて**発火させる**。加えて正常なものを与えて**沈黙させる** |
| 分類する `#eval` | 各バケツに既知の構成員を 1 つ入れる。個数を報告する前に構成員を 1 つ復号する |
| 定理 | 点で真であることを `#guard` で確かめる。加えて**実際の消費者に当てる** |

**両側が要る。** 欠陥を検出できることだけ確かめても、**常に赤を返す道具と区別がつかない**。

**定理の行が最も重要である。** 満たせない仮説を持つ定理は、満たせる定理と
**まったく同じようにコンパイルされる** — 分岐は discharge され、公理も清潔で、
ビルドも通る。この repo に実例があり (`asm_generalB`、5 分岐中 4 つ証明済み、
仮説がどの行でも偽)、気づいたのは実際の行を 1 つ通そうとした時だけだった。
だから**補題を書いたら、それを使う場所を 1 つ作って通す**。使われない補題は、
真であることしか分からない。

## 2. 種類ごと

### 証明を作る依頼

依頼文に書くべきもの (この文書には書けない、毎回変わる部分):

- 目標の定理を 1 つ、正確な文で。
- **今リポジトリにある名前の一覧。** 「モジュールにある」では足りない。
- 経路の判断。**閉じていると分かっている経路は、閉じている理由ごと明示的に禁止する。**
  さもないとそこへ向かう。
- 難所の予想。

**補題は閉じた順に、それぞれ名前を付けて残す。** 4 本のうち 3 本が閉じて 4 本目が正確に
述べられている状態は成果である。4 本まとめて止まっている状態は成果ではない。

### 公理の掃除を頼む依頼

- **文を 1 文字も変えない。** 名前も、束縛も、結論も。変えてよいのは `:=` の後ろだけ。
  こちらで全定理の文を突き合わせる。
- 既知の発生源は 2 種類ある。どちらもこのリポジトリで実際に起きた。

  | 形 | 直し方 |
  |---|---|
  | `omega` が**算術でない**目標を閉じている (矛盾した仮定から等) | `rw [if_neg (by omega), …]` や `intro h; exact absurd h (by omega)` で、`omega` を算術の部分目標に留める |
  | `simp only [beq_self_eq_true, if_true]` を `if` に当てる | `rw [if_pos (by rfl)]` |

- **タクティクの形で疑ってはいけない。公理を印字して疑う。**
  「決定手続き系のタクティクが非算術目標を矛盾で閉じれば汚れる」は一度そう書いて反証された。
  最小の例では汚れない。
- **切り分けは、宣言を 1 段ずつ組み直して各段で公理を印字する。依存関係を辿らない。**
  タクティクが入れた公理には辿るべき定数が存在しないので、
  「参照している名前は全部きれいなのに、この定理だけ汚い」という一見ありえない形になる。
  これは矛盾ではなく、原因がタクティクであることの合図である。

### 測定を頼む依頼

- **証明する前に、その文が真であることを `#guard` か `#eval` で確かめる。**
  偽の文を証明しようとして時間を使わせない。
- **「違反 0」が出たら、それが定理だからか、コーパスが届いていないからかを区別する。**
  証拠になるのは前者だけである。区別できないなら「測定して綺麗だった」ではなく
  「私の試験集合はこの場合に届かない」と報告する。
- 分類器を使ったら、**バケツの中身を最低 1 つ手で復号してから**個数を報告する。

## 3. 「できない」という結果について

**経路が閉じていることを理由付きで報告するのは、成果である。** 強引に証明を作るより価値がある。

実例。ある依頼で「`runAux` の append 補題を作れ」と指示したが、作業役の報告で
`runAux` が `++` について分解しないことが分かった — 構造判定がリスト全体を読み、再帰が
メモ表を持ち回るため。**指示した形の補題は最初から存在しなかった。** これが分かったことで
経路を変え、そちらは動いた。

だから、次のいずれかに当たったら、強引に進めずに報告する。

- 目標の文が偽である (反例を付ける)。
- 指示された補題が存在し得ない (理由を構造で述べる)。
- 指示された経路が、こちらの知らない理由で閉じている。

行番号と、判断の根拠になった定義を添える。
