THE RUNG FAMILY'S SEQUENCE IS NOT `fsC` — measured 2026-08-10
=============================================================

Measured before dispatching any proof work at `cert_epsN`, and it refutes the
obvious statement of it.

THE OBVIOUS STATEMENT, AND WHY IT IS WRONG
------------------------------------------
`Evidence/SqV.lean` §23 leaves `cert_epsOmega` carrying one hypothesis:

    cert_epsN (n) : Certified (Evidence.Cert.epsM n) (Evidence.WF.fsEW n)

Read naively, its `Certified.lim` identity premise would be discharged by showing
the BMS expansions of `epsM n` denote the T(M) fundamental sequence `fsC` of the
row's term.  MEASURED, `Trans.oR (BMS.expand (epsM (k+1)) n) == some (fsC (fsEW (k+1)) n)`:

    k = 0 :  [true, false, false]
    k = 1 :  [true, false, false]
    k = 2 :  [true, false, false]

**Only n = 0 agrees.**  Concretely at k = 0:

    fsC (ε_1) n              = ε₀,  ε₀+ε₀,  ε₀+ε₀+ε₀, …          (ε₀·(n+1))
    oR (expand (epsM 1) n)   = ε₀,  ω^(ε₀·2),  …                  a TOWER over ε₀·2

This is exactly what `Evidence/Cert.lean` §20 records in prose and what the ε_n
ladder finding in `Evidence/SqV.lean` §23 measured from the other side: *the ε_ω
row's expansions are the ladder's own rungs, but each RUNG's expansions leave the
ladder for a tower family one level down.*  Here it is, as numbers, on the object
`cert_epsN` is about.

WHAT THIS DOES AND DOES NOT RULE OUT
------------------------------------
It does NOT rule out `cert_epsN`.  `Certified.lim` takes the sequence `fs'` as a
PARAMETER — the identity premise is `∀ n, Certified (expand M n) (fs' n)`, and the
order clauses only require `fs'` to be increasing, below the row, and cofinal.
**Any cofinal increasing sequence is admissible**, so the certificate may use the
tower family rather than `fsC`.

It DOES rule out the proof anyone would try first, and it would have been found
only after building the wrong identity — which is why it was measured first.

CONSEQUENCE FOR THE NEXT PIECE OF WORK
--------------------------------------
`Cert` §21 supplies the expansion half for all `k` and all `n`:

    expand_epsM_succ (k n) : expand? (epsM (k+1)) n = some (rungM k n)
    rungM k n = epsM k ++ ((List.range n).map (rungBlock k)).flatten
    rungBlock k j = [j+1, 0] :: List.replicate (k+1) [j+2, 1]

so the open question is the ORDINAL side: what closed form does `oR (rungM k n)`
take, and is that family increasing, below `fsEW (k+1)`, and cofinal in it.
**Measure the closed form before stating it.**  The `fsC` reading above is the
first candidate anyone would write down and it is false.

So the closed form is the WF lane's own `fsEsucc`, which `Evidence/Cert.lean`

WHAT ACTUALLY BLOCKS `oR_rungM`
-------------------------------
Not the ordinal mathematics.  The identity reduces, via `expand_epsM_succ_total`
and `Rows.ProofsB.R3.e3_val`, to exactly:

    Trans.oR (BMS.expand Rows.ProofsB.R3.m0 n) = Trans.o? (BMS.expand Rows.ProofsB.R3.m0 n)

`Trans/Recal.lean` has **no symbolic bridge from the recalibrated `oR` to the
retracted `o?`**.  The row lemmas prove the `o?` reading; the certificate side
speaks `oR`.

**A bridge cannot be stated unconditionally.**  `o?` is the RETRACTED translation
and is wrong at and above `(0,0)(1,1)(2,1)(2,0)`, so any `oR = o?` lemma has to
carry a hypothesis confining it to where the two agree.  That is a real piece of
work, not a rewrite, and it is a DIFFERENT KIND of obstruction from everything
else in this file: the ordinal side is settled and the two halves of the project
simply speak different readers.

**CORRECTION TO A DOCUMENTED FACT.**  Several files in this repo say `o?` is wrong
"at and above `(0,0)(1,1)(2,1)(2,0)`".  Measured, **11 matrices STRICTLY BELOW that
matrix already disagree**, the first being the loop-back matrix
`(0,0)(1,1)(2,1)(1,1)(2,1)`.  A bridge stated at the recorded boundary would be
FALSE.  The recorded boundary is where the ORACLE audit found `o?`'s first wrong
VALUE; it is not where the two readers first diverge, and those are different
facts that the documentation ran together.

**AND THE ORDER CUT ALONE IS NOT ENOUGH.**  `Matrix = List (List Nat)` admits
malformed heights: `[[0], [1,0,0]]` is below the loop boundary and the readers
still disagree, because the recalibrated reader rejects its height-three column
while `o?`'s one-row fallback accepts it.  The bridge's hypothesis needs a
well-formedness conjunct as well as the order cut.

Standardness does not separate: the yaBMS `bms -s` reference classified all 607 as
standard, `(255, 352, 0, 0)`.  `BMS.Standard` is a reachability `Prop` with no
decision procedure here, which is why that check went through the reference
executable rather than a Lean predicate.

STILL OPEN: the bridge itself.  Unfolding `Trans.oR`/`Trans.Recal.oR`/`Trans.o?`
reaches an algorithm-equivalence obligation for which `Trans/Recal.lean` exports no
lemma.  The exact failing point is kept as a comment in
`lean/scripts/reader_agreement.lean` rather than as a broken proof.


APPENDED — BOTH ROUTES ARE CLOSED, AND THE SECOND REASON IS STRUCTURAL
======================================================================

Route (b), proving `oR_rungM` directly in `oR` without touching `o?`, was tried.
It is closed too, and the reason is a fact about this project rather than about
this theorem.

    file                 theorems   #guards

    Trans/Dict.lean             0        44
    Trans/Pair.lean             0        23
    Trans/StageC.lean           0        83
    Trans/Lemmas.lean           8         0

`oR = (1 + ·) ∘ dict ∘ transPort ∘ ofMatrix` is a pipeline of whole-matrix
computations, and **every `oR` fact in this repository is a `#guard` or a `decide`
at a concrete matrix.**  There is no equation for `oR (M ++ block)`, so an `∀ n`
statement has nothing to induct on.  The base `oR (rungM 0 0) = some (fsEsucc 0 0)`
is `rfl`; the step has no lemma to take.

**THIS IS NOT A GAP IN A PROOF, IT IS A MISSING LAYER.**  `oR` is a VALIDATED
COMPUTATION — 174 `#guard`s across `Trans/`, an oracle table, negative controls —
and validation at points is not an API.  Anything quantified over `n` on the `oR`
side is blocked until `Trans/Recal.lean` grows equation lemmas, and the size of
that work is set by `ofMatrix` / `transPort` / `dict`, not by any ordinal question.

WHAT SURVIVES: `expand_epsM_succ` (all k, all n), `rungM_zero`, `rungM_succ`, the
`n = 0` reading, and §21.1's 24-point measurement.  **The ordinal side of
`cert_epsN` is settled.  The reader side is where this line stops**, and it stops
for a reason that would block any other `∀ n` fact about `oR` equally.
